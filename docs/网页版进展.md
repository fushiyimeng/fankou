## 1. 桌面版：修了什么、加了什么

### 1.1 修的 bug：换底牌时选中的牌顶部被切

**文件**：`src/FanKou.Ui/Controls/HandPanel.cs` → `ComputeLayout()`

**现象**：见项目根目录的 `2.png`（用户提供的截图）。换底牌时选中（金边）的牌会往上浮，
浮起来的那一截**被控件顶部切掉**，而牌的左上角正好是点数——于是认不出是什么牌。
第二行最明显：K♣ / 5♣ / 4♣ / 3♣ 的点数上半截没了。

**根因**：第一行从 `y = 4` 开始摆，选中/悬停要上浮 `raiseOffset`
（换底对话框里约 21px），于是实际位置是 `4 - 21 = -17`，跑出控件顶部。

**为什么以前没暴露**：自带牌面的点数画得又大又靠下，切掉 17px 还能认出来；
换上真实扑克牌面（点数紧贴左上角）就原形毕露了。**这不是新牌面引入的，是它把老雷踩响了。**

**修法**：顶部预留出浮起的空间，牌相应矮一点。实测代价：

| 场景 | 改前牌高 | 改后牌高 |
|---|---|---|
| 换底对话框（2 行） | 148 | 137 |
| 主界面手牌区（1 行） | 182 | 156 |

**用户已经同意这个取舍**（牌小一点，换点数看得见）。

**验证状态**：✅ 用 `--render-swap` 渲图对比过（选中 3 张，顶部完整）。

### 1.2 新增「托管」（AI 代打）

**文件**：`src/FanKou.App/GameController.cs`、`src/FanKou.App/MainForm.cs`

出牌区多了一个「托管」按钮，点一下交给电脑代打，按钮变成「收回托管」，随时收回来。

**实现要点**：
- `GameController.AutoPlayHuman` 从 `{ get; init; }` 改成 `{ get; private set; }`，
  新增 `SetAutoPlay(bool)`。
- `SetAutoPlay(true)` 时如果正卡在等你出牌（`_humanPending` 非空），会立刻调 `Pump()`
  把这一手推给 AI，不用干等下一次节拍。
- 座位分流仍靠 `AutoPlayHuman` 这一个开关（原 `Pump()` 里那条判断）。
- 托管用**你自己座位那副脑子**（`_brains[HumanSeat]`），也就是菜单里选的对手强度那档。

**验证状态**：⚠️ 只验证了"一开始就托管"这条路径（`--autoplay 1` 跑通一整局）。
**"打到一半点托管"没实测过。**

### 1.3 新增「出牌超时兜底」（60 秒）

**文件**：同 1.2

轮到你出牌后开始读秒，标题栏显示 `● 你的回合 (45)`。**超 60 秒**没动作就替你出一手。

**实现要点**：
- `GameController` 新增 `_humanTimer`（1 秒一跳）、`HumanSecondsLeft`、
  `CountdownChanged` 事件。
- 读秒只在 `PendingDecision.NeedPlay` 时启动——**叫主和换底不做兜底**，
  那两步要自己拿主意，电脑替你定了不合适（真有事请点「托管」）。
- 超时后走 `SubmitPlay`，所以**替出的那一手照样能按「撤回」退回来**。
- 牌局记录里会留一条 `⚠ 超过 60 秒没动作，电脑替你出了一手`。
- 界面侧为了不整屏重画，倒计时单独走 `CountdownChanged` → `MainForm.UpdateTurnLabel()`，
  只更新那一格。

**验证状态**：❌ **完全没实测**（60 秒太长，没构造自动化验证）。逻辑上看是对的，但请实际试一次。

**待定**：用户问过要不要给叫主/换底也加超时，还没定。现在是"不加"。

### 1.4 新增崩溃日志

**文件**：`src/FanKou.App/Program.cs`

**背景**：这程序之前**完全没有日志落地**。「牌局记录」菜单只是内存里的一份列表，
程序一关就没了——出事之后完全无从查起（用户这次遇到 bug 时就没抓到任何东西）。

**做法**：`Main` 拆成包装器 + `Run()`，挂上 `AppDomain.UnhandledException` 和
`Application.ThreadException`，未处理异常追加写到 **exe 旁边的 `crash.log`**
（带时间戳 + 完整堆栈）。写不出来就算了，不在崩溃路径上再抛。

**验证状态**：❌ 没实测（没故意制造崩溃）。编译通过。

## 2. 网页版：做到哪了

### 2.1 项目结构

新建了 3 个项目，都已加进 `FanKou.slnx`：

| 项目 | 说明 | 状态 |
|---|---|---|
| `src/FanKou.Session` | net10.0 类库，引 Core + Ai | **空壳**（只有 csproj，删了模板的 Class1.cs） |
| `src/FanKou.Web` | Blazor WebAssembly + PWA | 骨架 + 牌面能显示 |
| `tests/FanKou.Session.Tests` | xUnit，引 Session | **空壳** |

**为什么要单独一个 `FanKou.Session`**（而不是把驱动逻辑塞进 Web）：
1. 它 TFM 是 `net10.0`，能被 xUnit 项目引用 → 驱动层可以做自动化测试
   （塞进 `browser-wasm` 的项目里，测试项目引用它会非常别扭）；
2. 下一期做联机服务端（Linux）时，服务端要的东西正好就是它（引擎 + 座位分配 + 节拍 + 快照），
   不用再写一遍。

**`FanKou.Web.csproj` 里几处要紧的**：
- `<InvariantGlobalization>true</InvariantGlobalization>` —— 必须显式覆盖。
  根 `Directory.Build.props` 设的是 `false`，那会把 ICU 文化数据（约 2MB）打进包。
  Core/Ai 里没有文化敏感操作（排序全按枚举和整数），关掉是安全的。
- 引用 `FanKou.Session`。
- 把根目录的 `rules.json` 和 `玩法说明.md` 复制成 `wwwroot` 下的静态资源
  （md 落地名用 ASCII 的 `rules-full.md`，免得浏览器 fetch 时还要处理中文路径编码）。
- **没开 AOT**（要装 `wasm-tools` 工作负载，而 AI 整局才 0.5ms，解释器绰绰有余）。

### 2.2 牌面素材（重要）

从 GitHub 拉的 **CC0 1.0（公共领域）** 扑克牌：
`https://github.com/AustinGabriel/Public-Domain-and-CC0-Playing-Cards`

- **授权**：CC0 1.0 Universal，最宽松，商用都行。
- **已确认**：54 张（含大小王）+ 牌背，**全部纯 path 绘制，没有一个文件含脚本**。
- **viewBox 统一是 `0 0 1500 2100`**（宽高比 0.7143）。
- 位置：
  - 网页版（SVG）：`src/FanKou.Web/wwwroot/skins/cc0/`（55 个文件 + `index.json`）
  - 桌面版（PNG）：`skins/CC0-Public-Domain/`（55 个 PNG + `skin.json`）

**一个待优化的点**：花牌（J/Q/K）文件很大——`CK.svg` 704KB、`CQ.svg` 644KB，
因为它们是从位图描摹出来的，路径点极密；数字牌只要 4~12K。
**建议用 SVGO 降一下坐标精度**（`--precision=1` 或 `2`），能瘦很多。
（试过改用同仓库的 PNG 版，反而更大——花牌 700K~1MB，数字牌也比 SVG 大十倍，所以 SVG 是对的。）

**大小王映射**：按「红王 = 大王、黑王 = 小王」放的。**这条没跟用户确认过**，接手时问一下。

### 2.3 网页版已完成的组件

| 文件 | 作用 |
|---|---|
| `Services/CardAssetSet.cs` | 网页版的皮肤解析。桌面版是"按候选文件名去磁盘挨个找"，浏览器不能枚举目录也发不出几十个探测请求，所以改成"按候选名在一份 `index.json` 索引里查"。**认名字的规则仍然用 Core 的 `CardFileNames`**，两版共用同一套命名契约 |
| `Components/Cards/CardView.razor` | 一张牌的显示（只负责长什么样，不管摆在哪）。`Card` 为 null 时画牌背 |
| `Pages/Preview.razor` | `/preview` 路由，把整副牌平铺出来肉眼检查 |
| `wwwroot/css/app.css` | 牌面样式（追加在原模板样式后面） |

**验证状态**：✅ `dotnet run --project src/FanKou.Web` 后开 `/preview`，
无头浏览器截图确认 **54/54 张全部认到**，牌背正常。

**注意**：`CardView` 的参数叫 `Skin` 不叫 `Assets`——`Assets` 会撞 Blazor 基类
`ComponentBase.Assets`（编译警告 CS0108）。

### 2.4 桌面版的新牌面

`skins/CC0-Public-Domain/` 里是 SVG 转出来的 PNG（**500×700**，保持素材自己的 5:7 比例）。

- 转换脚本在临时目录（`%TEMP%\svg2png\convert.js`，用 `sharp`），**没进版本库**。
- 也复制了一份到 `src/FanKou.App/bin/Release/net10.0-windows/win-x64/skins/CC0-Public-Domain/`，
  这样游戏能扫到（`CardSkin.Discover()` 扫的是 exe 旁的 `skins`）。
  **注意 `bin` 是构建产物，重建可能丢**，所以源留在项目根的 `skins/`。
- 桌面版牌框比例是 **0.70**，素材是 **0.7143**，差 1.4%，上下各留一丝白边，肉眼看不出来。
- **两副牌会长得一模一样**：桌面版原本在第二副牌角上画小圆点做区分，
  但外挂图片是整张盖上去的，会把那个标记盖掉。双扣里两副牌本来就相同，通常无所谓。

## 4. 关键决策与理由

| 决策 | 理由 |
|---|---|
| 网页版用 **Blazor WebAssembly** | `FanKou.Core`（4354 行）+ `FanKou.Ai`（1438 行）是纯 `net10.0`、零 Windows 依赖，能**原样编进浏览器**，规则和 AI 一行都不用重写。代价是首次加载要下几 MB 运行时 |
| 牌面用 **内联 DOM + 图片/SVG**，不用 Canvas | `<img>` 的点击、悬停、CSS 响应式布局全部免费；Canvas 要自己做命中测试、devicePixelRatio、resize 重绘 |
| 单独开 **`FanKou.Session`** 层 | 见 2.1 |
| 牌面比例从 0.70 改成素材的 **0.7143** | 用素材自己的比例就不用留白。桌面版还是 0.70（差 1.4%，无所谓） |
| 超时**只兜底出牌**，不做叫主/换底 | 那两步要自己拿主意（**待用户最终确认**） |
| **没开 AOT** | 要装 `wasm-tools`，构建从 30 秒变 10 分钟；而 AI 整局 0.5ms，解释器绰绰有余 |

### 7.1 线上地址

**对外地址就是 `https://fankou.fushiyimeng.cn/`** —— 走的是既有 443 那一套
（和 astrbot / napcat / files 同一个入口、同一张泛域名证书）。

| 项 | 值 |
|---|---|
| 对外地址 | **https://fankou.fushiyimeng.cn/**（443 反代） |
| 直连端口 | http://fankou.fushiyimeng.cn:8080/（容器自己的口，主要留给内网和调试） |
| 落地 | N100 `/opt/go-bot/fankou/wwwroot` |
| 服务 | 独立容器 `fankou-web`（`nginx:alpine`），专端口 **8080**，`restart: unless-stopped` |
| 配置 | `/opt/go-bot/fankou/{nginx.conf,docker-compose.yml}`，源在仓库 `tools/deploy/` |

**只解析到 AAAA（ddns-go 里 IPv4 是关的），所以整站只有 IPv6 能访问**——这一点和主域、
astrbot 那几个完全一样。用没有 IPv6 的网络（部分 Wi-Fi、部分公司网）打不开是正常的，
拿 4G/5G 流量试最准。**2026-10-16 第一次上线时用了 `:8080` 这个地址，外网打不开，
就是因为家宽大概率封了 8080 这个口**，所以补了下面这条 443 的路。

443 那个 vhost 写在 portal 容器的 `/opt/go-bot/portal/edge.conf` 末尾，
内容是 `proxy_pass http://fankou-web:80`——所以 `fankou-web` **必须**挂在
`go-bot_astrbot_network` 上（`tools/deploy/docker-compose.yml` 里那两行 `networks`，
删了 443 就会 502）。改完用：

```bash
docker exec portal nginx -t && docker exec portal nginx -s reload
```

**不用重启 portal**。⚠️ 这个 vhost **故意没加 HSTS**：加了之后浏览器会把
`http://fankou.fushiyimeng.cn:8080` 也升级成 https，而那个口是明文 HTTP，等于自己把直连口锁死。

nginx 那边开了 `gzip_static`，发的是 `dotnet publish` 生成的 `.gz`（部署包不传 `.br`，
因为官方 nginx 镜像没有 brotli 模块）。

### 7.2 怎么更新

## 8. 2026-10-16 晚：用户报的两个问题

### 8.1 撤回之后牌自己又打出去了（已修）

**现象**：点「撤回」，回到"轮到你出牌"，然后**大约 1 秒后电脑自己替你出了一手**。

**根因**（在 `GameSession`，是我移植时带进来的）：

读秒是靠"下一拍"续命的，而续命的入口只有 `Plan()` 里
`if (_humanPending is null) { … StartHumanCountdown(pending); }` 那一段。
`Undo()` 是**直接**设 `_humanPending = _engine.Pending` 的，绕过了这段，
于是 `_humanSecondsLeft` 还停在 0。循环随即拿到 `Step.HumanTick`，
第一跳就把 0 减成 -1、判定"超时"，立刻叫电脑替你出牌。

桌面版没这个毛病，因为那边超时是 WinForms 计时器：撤回时它被 Stop 掉了，
之后没人再把它 Start 起来，所以是"没有读秒"而不是"立刻超时"——
移植到 async 循环之后，"没有读秒"和"读秒已经归零"变成了同一个状态，雷就响了。

**修法**：`Plan()` 里补一条——真人待决策、但读秒没有在走时，重新起表：

```csharp
else if (_humanSecondsLeft <= 0 && IsTimed(pending))
{
    StartHumanCountdown(pending);
}
```

**回归测试**（`SessionDiagnostics.UndoAsync` 里）：撤回后等 1.5 秒，
手牌数不许变。改之前这条必然红。

### 8.2 发牌加快，以及 30 秒定牌

用户要求：**发牌加快，但能定牌的时候要停下来等，这个等待最多 30 秒。**

| 项 | 改前 | 改后 |
|---|---|---|
| `DealRoundMs`（每轮发牌） | 500ms（整副 12.5 秒） | **100ms（整副约 2.5 秒）** |
| 出牌读秒 `HumanTimeoutSeconds` | 60 秒 | 60 秒（不变） |
| 叫主/反主读秒 `CallTimeoutSeconds` | **没有**（会一直等） | **30 秒** |

要点：

- 发牌快慢**不影响"抢先叫主"**。引擎每一轮发完就查一圈"谁现在叫得出来"，
  有人能叫就**立刻停下来问那一家**，玩家不需要在 100ms 内反应。
  所以加快的只是动画，窗口一点没少。
- 叫主超时后走 `BrainDecider`，用**你自己座位那副脑子**替你定，和出牌超时同一套；
  牌局记录里会留一条 `⚠ 超过 30 秒没动作，电脑替你叫了`。
- **换底牌仍然不读秒**（真的得自己拿主意，电脑替你扣 8 张下去后果太重）。
- 叫主框里现在显示 `还有 N 秒，到点电脑替你定`。

⚠️ **桌面版没有跟着改**：那边的 `GameController` 还是 500ms、叫主也没有超时。
要一致的话得改 `src/FanKou.App/GameController.cs` 再重新编译 Release
（Release 本来就还欠着，见第 0 节）。

## 9. 2026-10-16 深夜：联机对战上线

### 9.1 怎么玩

- 线上 **https://fankou.fushiyimeng.cn/** 现在是大厅：**单人（打人机）** / **创建房间** / **加入房间**。
- 创建房间会生成一个 **4 位数字房号**（1000~9999，同一时间全局唯一），发给朋友，他们在大厅输入就能进来。
- **房间默认没有人机**，四个位子凑满才能开局；人不够房主点「添加人机」补。
- 座位按加入顺序分：**南 → 北 → 东 → 西**。前两个是对家，所以两个人玩刚好一队，另外两家交给电脑。
- 谁掉线，他的位子自动转托管（电脑替他打），列表里显示「掉线（托管中）」；F5 重进同一个房号能顶回自己的位子。
- **单人模式（/solo）还是原来的样子**：一进去就有三家电脑。

### 9.2 结构

| 件 | 位置 | 说明 |
|---|---|---|
| 客户端 | `src/FanKou.Web`（`/` 大厅、`/solo` 单人、`/room[/{房号}]` 联机） | 浏览器里**不跑任何规则**，只显示 + 发动作 |
| 协议 | `src/FanKou.Protocol` | 客户端和服务端**共用同一份 DTO**，不会两边抄歪 |
| 服务端 | `src/FanKou.Server` | Kestrel + WebSocket，房间管理，**规则引擎跑在这里** |
| 驱动层 | `src/FanKou.Session` | 同一套 `GameSession`：单人时一个座位等人，联机时最多四个座位等人 |

链路：`浏览器 → https/wss://fankou.fushiyimeng.cn → portal(443) → fankou-web(80) → host.docker.internal:8081（systemd 里的 fankou-server）`。

- 服务端二进制：`/opt/go-bot/fankou/server/FanKou.Server`（linux-x64 自包含单文件，97MB，目标机不用装 .NET）
- systemd 单元：`fankou-server.service`，`FANKOU_URLS=http://0.0.0.0:8081`、`Restart=always`
- **只绑 IPv4**：N100 的 IPv6 没有防火墙，用 `http://*:8081` 会把这个口直接晾在公网上。
  现在这样只有容器和局域网连得到，对外统一走 443。

### 9.3 协议（JSON over WebSocket）

客户端 → 服务端：`create` / `join` / `addBot` / `removeBot` / `start` / `next` / `call` / `bottom` / `play` / `ping`
服务端 → 客户端：`joined` / `room` / `state` / `result` / `error` / `pong`

三条硬规矩：

1. **座位以连接为准，不信消息里的座位号**（不然谁都能替别人出牌）。
2. **牌只传 Id（那个 0..161 的整数）**，两边用 `Card.FromId` 还原，不传对象。
   ⚠️ 反算花色不能写 `id / 32`：Joker 是第 5 个花色（枚举值 4），大王会越过一个 32 的边界。
3. **手牌、锅底各发各的**：`state.hand` 只放收信人自己那 25 张；`state.bottom` 在 `BottomRevealed` 之前是空数组。
   联机自检里专门有一条断言盯着这个。

### 9.4 修掉的一个真 bug：`GameSession` 不是线程安全的

单人版在 WASM 里跑，从头到尾一个线程，所以一直没暴露。搬到服务端以后，
**客户端动作从 WebSocket 线程进来，驱动循环跑在自己那条任务上**，两边同时动引擎。
表现是自检**时好时坏**（有时候一局打不完）。

修法：`GameSession` 里加一把 `_gate`，循环的 `Plan()` / `Execute()` / `TickHumanCountdown()`
和所有公开入口（`Submit*` / `Undo` / `SetAutoPlay` / `SetSeatKind` / `ApplyOptions` / `Start`）都加锁。
锁只包同步代码——等节拍的部分在锁外面，不然整条循环会被锁死。
改完连跑 5 次联机自检 + 单人自检全绿。

## 10. 2026-10-16 深夜：房间改成"等待室 + 观战席 + 指定座位"

### 10.1 现在的房间长什么样

- 创建房间之后是**停下来等人**，不是直接开打。
- **4 个牌桌座位按「南 → 北 → 东 → 西」列**（不是枚举顺序，枚举顺序是东南西北，看着别扭）。
- **3 个观战席**：进去只看得见牌桌，**看不到任何人的手牌**（服务端对观战连接发的 `hand` 是空数组、`pending` 是 null）。
- 每个座位的按钮：
  - 空位 → `加人机`（房主）/ `坐这儿`（任何人）
  - 人机 → `顶掉它`（坐过去，人机没了）/ `删掉`（房主）
  - 别人 → `换过来`（**两个人对调**）
  - 自己 → 标一个「你在这儿」
- 观战席空着就有 `去观战`。

规则：**换座位/上桌/下桌/加人机都只在开局前有效**；开局之后座位锁死（掉线仍然是自动托管，重进房号能顶回原位）。

### 10.2 又抓到一个会"把房间搞死"的 bug

自检加完新场景之后又开始时好时坏。加了诊断（把最后看到的状态打出来）之后定位到：

> 卡在换底牌那一步，状态栏写着「叫主摆出来的明牌不能扣进底牌」。

根因在 **`GameEngine.Apply` 是"边改边判"的**：它先把 `Pending` 清掉、再校验，校验不过就抛异常。
而 `GameSession.Submit` 的 catch 只是把异常咽下去、设个状态文字——
此时引擎的 `Pending` 已经是 null，驱动循环的 `Plan()` 看到"没有待决策、也不在发牌"，
就安安静静地等一个永远不会来的信号。**整局就此卡死，再也推不动。**

也就是说：**任何人往服务端发一手非法的牌，就能把这间房弄死。**

修法是"进引擎之前先挡"：

- `SubmitPlay` 先跑 `ValidateSelection(seat, cards)`（跟界面用的是同一份判据），不合法就只驳回、不推进；
- `SubmitBottomDiscards` 先查"正好 8 张 / 都在可挑范围 / 不含叫主明牌"；
- `SubmitCall` 先确认那个叫法确实在当前候选里（过期消息或手搓协议都会带一个不在候选里的对象）。

`ValidateSelection` 顺手从"只看本机座位"改成按座位传参——联机时每个座位都要能校验。

自检也补了对应的一条：换座位、**给人机指定座位**、观战位看不到手牌，连跑 6 次全绿。

### 10.4 换座位之后，"自己"仍然在屏幕下方

第一版把 `TableView.From(StateDto)` 的 `HumanSeat` 写死成了南，
结果坐到东家的人会看到**自己那一手横在屏幕右边**——像是侧着身子打牌。

牌桌的方位是靠 `rel = (seat - HumanSeat + 4) % 4` 算的（0=下、1=左、2=上、3=右），
所以正确做法是**把玩家真实的座位传进去**：换座位转的是东南西北的方位，不是你坐的位置。

现在 `TableView.From(state, humanSeat)`，`Room.razor` 传自己的座位（观战的人用南，反正看不到手牌）。
实测：换到东家之后 → `rel-0=东 家`（自己在下）、`rel-2=西 家`（对家在正对面）、南/北分列左右。
